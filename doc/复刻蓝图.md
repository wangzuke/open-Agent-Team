# A. 系统总览

这个项目不是“一个中心化 orchestrator 管所有 agent”的架构，而是一个混合型 multi-agent coding system：

- 主干是统一的单线程 LLM/tool loop：`main.tsx -> REPL/QueryEngine -> query() -> tool execution -> 再入 query`，入口在  
  `src/main.tsx:3030`、  
  `src/screens/REPL.tsx:2772`、  
  `src/QueryEngine.ts:292`、  
  `src/query.ts:219`。
- 在这条主干之上叠了两套多智能体机制：一套是 `AgentTool -> runAgent()` 的子代理/后台代理体系，另一套是 `TeamCreate/SendMessage/Task* + mailbox + task board + swarm backend` 的长期 `team/swarm` 体系，关键点在  
  `src/tools/AgentTool/AgentTool.tsx:196`、  
  `src/tools/AgentTool/runAgent.ts:248`、  
  `src/tools/shared/spawnMultiAgent.ts:1088`、  
  `src/utils/tasks.ts:190`、  
  `src/utils/teammateMailbox.ts:43`。
- 它更接近“planner/delegate + background worker + swarm mailbox/task-board”混合模式，而不是纯黑板系统、纯 actor system，或单一 supervisor tree。
- 高确定性结论：这里确实有真实 multi-agent 机制，但它是分布式实现，不存在一个单独的 `AgentManager / Scheduler` 核心类。

# B. 架构分解

- **启动与会话装配模块**：负责 CLI/环境初始化、主线程 agent 选择、初始 `teamContext` 注入，关键在  
  `src/main.tsx:2083`、  
  `src/main.tsx:3030`、  
  `src/replLauncher.tsx:12`；  
  它把 `prompt`、`tools`、`agentDefinitions`、`team state` 交给 `REPL/QueryEngine`。
- **主执行循环模块**：负责把 `messages/systemPrompt/userContext/systemContext` 送入模型，处理 tool use、重试、compact、continuation，核心是  
  `src/screens/REPL.tsx:2772`、  
  `src/QueryEngine.ts:675`、  
  `src/query.ts:219`；  
  这是所有 agent 形态共用的底层 loop。
- **Prompt 系统模块**：负责默认 prompt、agent prompt、coordinator prompt、teammate addendum、fork prompt 继承与拼装，关键在  
  `src/constants/prompts.ts:444`、  
  `src/utils/systemPrompt.ts:41`、  
  `src/coordinator/coordinatorMode.ts:111`、  
  `src/utils/swarm/teammatePromptAddendum.ts:1`、  
  `src/tools/AgentTool/forkSubagent.ts:107`；  
  它决定角色边界和职责分工。
- **Agent 定义与装载模块**：负责 built-in/custom/plugin agent 的 schema、覆盖优先级、frontmatter/json 解析，关键在  
  `src/tools/AgentTool/loadAgentsDir.ts:106`、  
  `src/tools/AgentTool/builtInAgents.ts:17`；  
  它不是 runtime class hierarchy，而是 declarative `AgentDefinition`。
- **子代理执行模块**：负责从 `AgentTool` 创建 agent，到 `runAgent()` 进入独立 query loop，再到前后台任务收束，关键在  
  `src/tools/AgentTool/AgentTool.tsx:577`、  
  `src/tools/AgentTool/agentToolUtils.ts:508`、  
  `src/tools/AgentTool/runAgent.ts:748`、  
  `src/tasks/LocalAgentTask/LocalAgentTask.tsx:466`；  
  它与主 loop 通过 `<task-notification>` 和任务状态衔接。
- **Swarm / teammate 模块**：负责 team 文件、backend 选择、tmux/iTerm2/in-process teammate 拉起和生命周期管理，关键在  
  `src/utils/swarm/teamHelpers.ts:64`、  
  `src/utils/swarm/backends/registry.ts:136`、  
  `src/tools/shared/spawnMultiAgent.ts:1088`、  
  `src/utils/swarm/inProcessRunner.ts:883`；  
  它与 task board 和 mailbox 紧耦合。
- **通信与共享任务模块**：负责 `SendMessage`、文件邮箱、任务板、owner/dependency/blocking 关系，关键在  
  `src/tools/SendMessageTool/SendMessageTool.ts:520`、  
  `src/utils/teammateMailbox.ts:134`、  
  `src/utils/tasks.ts:279`、  
  `src/tools/TaskUpdateTool/TaskUpdateTool.ts:1`；  
  这是 swarm 真正的协作骨架。
- **Tooling 与权限模块**：负责工具接口、工具池、MCP 合并、工具调用、hook/classifier/permission 决策、结果回写，关键在  
  `src/Tool.ts:158`、  
  `src/tools.ts:345`、  
  `src/services/tools/toolExecution.ts:337`、  
  `src/services/tools/toolOrchestration.ts:19`、  
  `src/services/tools/StreamingToolExecutor.ts:74`。
- **Context / memory 模块**：负责 `ToolUseContext`、subagent context cloning、session memory、auto/project memory、team memory sync，关键在  
  `src/Tool.ts:158`、  
  `src/utils/forkedAgent.ts:345`、

# C. 主执行链路

1. 启动时 `src/main.tsx:3030` 计算初始 `teamContext`，解析 CLI agent、system prompt、model、MCP、历史状态。  
2. `launchRepl()` 把这些状态交给 `src/screens/REPL.tsx:2793`；SDK/headless 则走 `src/QueryEngine.ts:184`。  
3. 在发起一次 query 前，系统先取默认 prompt / user context / system context：  
   `src/constants/prompts.ts:444`、  
   `src/context.ts:155`、  
   `src/context.ts:116`。  
4. `src/utils/systemPrompt.ts:41` 决定最终用 `coordinator`、`main-thread agent`、`custom` 或 `default` prompt。  
5. `src/query.ts:219` 把 `systemPrompt/userContext/systemContext/messages/toolUseContext` 送入模型，并在内部维护 assistant messages、tool results、continuation。  
6. 如果模型发出 tool use，`query()` 进入  
   `src/services/tools/toolOrchestration.ts:19`  
   或  
   `src/services/tools/StreamingToolExecutor.ts:74`，  
   再进入  
   `src/services/tools/toolExecution.ts:337`。  
7. 若工具是 `AgentTool`，则会进入两条分支：普通 `subagent/background agent` 走  
   `src/tools/AgentTool/runAgent.ts:248`；  
   `team teammate` 走  
   `src/tools/shared/spawnMultiAgent.ts:1088`。  
8. `runAgent()` 内部再次调用 `query()`，所以 agent 不是特殊引擎，而是“同一引擎上的隔离 query loop”；in-process teammate 在  
   `src/utils/swarm/inProcessRunner.ts:1175`  
   也复用这一点。  
9. 工具结果最终映射成 `tool_result`，必要时落盘，再并回下一轮 query 输入；后台 agent 则通过 `<task-notification>` 回到主线程，见  
   `src/tasks/LocalAgentTask/LocalAgentTask.tsx:197`、  
   `src/query.ts:1570`。  
10. 若上下文过长、streaming fallback、stop hook 失败，恢复逻辑仍集中在  
   `src/query.ts:709`、  
   `src/query.ts:1094`、  
   `src/query.ts:1267`。

# D. 多 Agent 机制专项分析

## Prompt system

- 系统提示词核心入口是  
  `src/constants/prompts.ts:444`  
  和  
  `src/utils/systemPrompt.ts:41`；  
  优先级硬编码为 `override > coordinator > mainThreadAgent > custom > default`，`appendSystemPrompt` 最后追加。
- 内建角色 prompt 分散在  
  `src/tools/AgentTool/built-in/generalPurposeAgent.ts:25`、  
  `src/tools/AgentTool/built-in/exploreAgent.ts:64`、  
  `src/tools/AgentTool/built-in/planAgent.ts:73`、  
  `src/tools/AgentTool/built-in/verificationAgent.ts:134`；  
  `coordinator` 在  
  `src/coordinator/coordinatorMode.ts:111`；  
  `teammate` 在  
  `src/utils/swarm/teammatePromptAddendum.ts:1`。
- Prompt 不是单模板，而是分层拼装：默认大 prompt + 动态 memory/user/system context + 角色 prompt 覆盖/追加 + fork 指令继承；fork 特例直接继承父 prompt 字节串以保证 cache 命中，见  
  `src/tools/AgentTool/forkSubagent.ts:42`。
- 工具说明主要不是文本拼进 system prompt，而是通过 tool schema 注入，见  
  `src/utils/api.ts:119`。

## Agent lifecycle

- 没有统一 Agent 抽象基类；配置层是  
  `src/tools/AgentTool/loadAgentsDir.ts:106`，  
  运行时载体是  
  `src/Tool.ts:158`  
  与  
  `src/utils/agentContext.ts:32`。
- 创建：`AgentTool.call()` 解析 `subagent_type/model/background/isolation/team_name/name/mode`，见  
  `src/tools/AgentTool/AgentTool.tsx:196`。
- 初始化：`runAgent()` 做 MCP 初始化、工具解析、hooks、skills、memory/system-context 裁剪，见  
  `src/tools/AgentTool/runAgent.ts:500`。
- 销毁：`runAgent()` 尾部集中回收 MCP、hooks、transcript/file/task 资源，见  
  `src/tools/AgentTool/runAgent.ts:816`。
- 恢复：后台 agent 可通过  
  `src/tools/AgentTool/resumeAgent.ts:42`  
  重建并继续执行。

## Coordination pattern

- 普通子代理侧是 `planner/delegate/worker` 模式：主线程通过 `AgentTool` 派活，worker 通过 `<task-notification>` 返回阶段结果。
- swarm 侧是 `shared task board + mailbox + leader-mediated permissions` 模式：任务通过  
  `src/utils/tasks.ts:279`  
  创建/认领/阻塞，消息通过  
  `src/utils/teammateMailbox.ts:134`  
  投递。
- `coordinator mode` 更像 prompt-level supervisor，而不是单独 scheduler；只暴露 `Agent/TaskStop/SendMessage/SyntheticOutput`，见  
  `src/utils/toolPool.ts:35`。

## Context / memory

- 核心上下文结构是  
  `src/Tool.ts:158`；  
  主线程、subagent、teammate 都围绕它运行。
- subagent 通过  
  `src/utils/forkedAgent.ts:345`  
  克隆 `readFileState`、`contentReplacementState`、`query chain`、`abort controller`，避免直接共享可变状态。
- session memory 是“后台 fork 提炼总结”，不是即时共享对象，见  
  `src/services/SessionMemory/sessionMemory.ts:272`。
- 长期 memory、team shared memory、task board、mailbox 是四套不同状态层；尤其不能把 task/mailbox 当成 memory 子系统。

## Tool use

- 工具接口统一在  
  `src/Tool.ts:362`；  
  工具池统一由  
  `src/tools.ts:345`  
  生成。
- Agent 如何拿工具列表：主线程先 `assembleToolPool`，再按 agent frontmatter/coordinator 模式二次过滤；subagent 再走  
  `src/tools/AgentTool/agentToolUtils.ts:122`。
- 调用协议是标准 tool schema + `tool_use / tool_result` block；结果可落盘再回写，见  
  `src/utils/toolResultStorage.ts:137`。
- 权限隔离并不只靠 tool 自己；它叠加了 policy/hook/classifier/UI 或 swarm leader 决策，入口在  
  `src/hooks/useCanUseTool.tsx:27`。

## Communication

- 子代理与主线程：`<task-notification>` XML 协议，见  
  `src/tasks/LocalAgentTask/LocalAgentTask.tsx:197`。
- teammate 间：文件邮箱 `~/.claude/teams/{team}/inboxes/{agent}.json`，消息结构是  
  `src/utils/teammateMailbox.ts:43`。
- 协议上存在显式结构化消息：`permission_request/response`、`sandbox_permission_*`、`plan_approval_*`、`shutdown_*`、`task_assignment`、`idle_notification`，都在  
  `src/utils/teammateMailbox.ts:394`  
  之后。
- `SendMessageTool` 是强制的显式 agent 间沟通工具，源码明确说普通输出不会被其他 agent 看见，见  
  `src/tools/SendMessageTool/prompt.ts:23`。

## Parallelism

- 单轮工具并行：由  
  `src/services/tools/toolOrchestration.ts:19`  
  和  
  `src/services/tools/StreamingToolExecutor.ts:74`  
  负责；并发只允许 `isConcurrencySafe()` 工具，结果提交仍按原顺序。
- 多 agent 并行：后台 subagent 通过  
  `src/tasks/LocalAgentTask/LocalAgentTask.tsx:466 + runAsyncAgentLifecycle`；  
  teammate 通过 `tmux/iTerm2/in-process backend` 独立运行。
- 独立性依靠 `AsyncLocalStorage teammate context`、`subagent context cloning`、独立 `abort controller`、任务文件锁、邮箱文件锁。
- 失败恢复分层处理：工具层有 `sibling abort / synthetic error`；query 层有 `compact retry / fallback / stop-hook retry`；worker 权限等待则靠 `mailbox + poller` 恢复。

# E. 复刻指南

如果从零复刻 `agent-teams`，必须先保留这些抽象：

- 一个统一 query loop，支持消息续写、tool use、tool_result 回注、重试/compact；这是所有 agent 共用引擎。
- 一个 declarative `AgentDefinition` 层，至少含 `agentType/prompt/tools/disallowedTools/model/effort/permissionMode/background/maxTurns`。
- 一个可克隆的 `RuntimeContext`，至少含 `messages/tools/appState/readState/abortController/agent identity`；必须支持父子隔离。
- 一个 `AgentTool` 等价物，用来创建普通 worker、fork worker、team teammate。
- 一个显式通信层；最小版可以先只做 `SendMessage + task notification`，完整版再加 mailbox 协议。
- 一个最小任务板；至少要有 `Task{id, subject, owner, status, blockedBy}`，否则 swarm 无法形成稳定协作。
- 一个工具池与权限层；至少要能给不同 agent 过滤工具，并支持 `leader/worker` 权限转发。
- 一个最小 memory 策略；最简版可以先只有 `session summary`，不必一开始就做 `teamMemorySync`。

## 最小可运行版本建议

- **Agent**：`main/coordinator`、`general worker`、`explore worker` 三种足够起步。
- **工具**：`Read/Search/Edit/Shell/Agent/SendMessage/TaskCreate/TaskUpdate`。
- **上下文**：主线程 `RuntimeContext`、子代理 `cloneContext()`、teammate identity context。
- **调度**：主线程 delegate，worker 独立 query，结果通过 `task-notification` 或 `SendMessage` 回主线程。
- 显式 agent 通信协议。
- 后台任务状态与结果回流机制。

## 可以简化的实现细节

- `team memory remote sync`
- `tool search deferred discovery`
- `tmux/iTerm2` 多 backend
- `attachment` 级别的高级 reminder / cache-safe fork 细节
- `coordinator mode` 的专用 prompt 文案，只保留其行为约束即可

# F. 风险与不确定点

## 高确定性部分

- 这是混合式 multi-agent 架构，不是伪多 agent。
- 核心不是单一 orchestrator class，而是 `query loop + AgentTool + runAgent + task/mailbox/swarm backend` 的分布式组合。
- `prompt`、`tooling`、`context`、`parallelism`、`task board`、`mailbox` 的主机制都能在源码中闭环。

## 推断成分较强的部分

- “没有全局 DAG scheduler”是根据只发现 `tasks.ts` 的 `claim/block/update` 逻辑推断的；源码里没看到独立 scheduler 类。
- “coordinator mode 主要是 prompt + tool filter”是当前快照可见结论，但 worker agent 具体定义缺一块源码。

## 当前代码中不完整的点

- `src/tools/AgentTool/builtInAgents.ts:56` 动态引用 `src/coordinator/workerAgent.js`，当前快照里未见对应 TS 源文件；因此 coordinator worker 的完整 `prompt/definition` 无法完全验证。
- 某些能力受 feature gate 控制，快照里能看到入口，但不一定都在当前构建启用。

如果你下一步要把这份分析转成真正的 `agent-teams` 实现蓝图，我建议直接按这 5 个包拆：

- `runtime`（query loop）
- `agents`（definition + spawn）
- `coordination`（task + message）
- `tools`（permission + execution）
- `memory`（context + summary）
